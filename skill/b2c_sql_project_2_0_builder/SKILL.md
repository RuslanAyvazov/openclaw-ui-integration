# Сборка B2C-витрины

Работать только с подготовкой витрин данных по S2T. Не придумывать отсутствующие
поля, ключи, типы, партиции или SQL-прототипы.

## Входные данные

До запуска получить:

1. Один файл `S2T.xlsx` с листом `Target columns`.
2. Формат хранения: `iceberg` или `parquet`.
3. SQL-прототипы верхнего `SELECT`: готовый `dml_scripts.json` или отдельные
   файлы `DML_inc.sql` и `DML_arc.sql`.

Для Iceberg требовать `DML_inc.sql` и `DML_arc.sql`. Для Parquet требовать только
`DML_inc.sql`. Полный контракт входов читать в
`{baseDir}/references/input-contract.md`.

При наличии S2T и выбранного формата вычислять ожидаемое число прототипов:
`таблицы × 2` для Iceberg, `таблицы × 1` для Parquet. Формат короткого диалога с
пользователем читать в `{baseDir}/references/communication-contract.md`.

## Выполнение

### Режим REST-интеграции с `uploadId`

Если в сообщении передан `uploadId`, не искать файлы самостоятельно и не
запускать shell-команды напрямую. Вызвать отдельный инструмент OpenClaw:

```json
{
  "uploadId": "<UPLOAD_ID>",
  "storage": "<iceberg|parquet>"
}
```

Имя инструмента: `b2c_build_from_upload`.

Если формат хранения не указан, использовать `iceberg`. Инструмент сам получает
workspace текущего агента от OpenClaw, открывает пакет
`uploads/<UPLOAD_ID>/`, находит `S2T.xlsx`, `DML_inc`/`DML_arc` в файлах
`.sql` или `.txt` и запускает `{baseDir}/scripts/run_from_files.sh`.

При успешном вызове вернуть пользователю пути `output.contextConfig`,
`output.dmlJson`, `output.martDirectory` и кратко подтвердить завершение сборки.
При ошибке показать полный текст ошибки инструмента без сокращений и не
придумывать отсутствующий результат.

### Режим B2C-SQL UI

Если системное сообщение говорит, что запрос пришёл из `B2C-SQL UI`, не запускать
сценарии навыка самостоятельно и не записывать `context_config.json`, `dm_res`
или SQL-файлы на диск. В этом режиме:

1. Кратко помочь пользователю собрать один пакет: `S2T.xlsx`, формат хранения и
   SQL-прототипы.
2. Направить пользователя к скрепке и кнопке «Проверить и собрать» в интерфейсе.
3. После нажатия интерфейс сам запускает те же детерминированные сценарии во
   временной файловой системе в оперативной памяти.
4. Не выводить `b2c-project`, JSON и содержимое файлов в ответе. После успешной
   сборки интерфейс сам предлагает открыть «Паспорт новой витрины».
5. При ошибке объяснить только полученный список исправлений; не придумывать
   обходной результат.

Следующие команды относятся только к прямому CLI-режиму OpenClaw.

1. После получения полного пакета не писать промежуточный ответ и не пересказывать
   SQL. Первым действием прочитать вложения и запустить поставляемый сценарий.
2. Если пользователь прислал отдельные SQL, не сопоставлять их рассуждением
   модели. Запустить `run_from_files.sh`: сценарий через SQLGlot сравнит точный
   набор полей внешнего `SELECT` с `validator.tables[].stg_table.columns`, соберёт
   `dml_scripts.json` и запустит всю цепочку:

```bash
bash {baseDir}/scripts/run_from_files.sh <S2T.xlsx> \
  --storage <iceberg|parquet> \
  --sql-file <первый.sql> \
  --sql-file <второй.sql> \
  --dml-json <dml_scripts.json> \
  --output-json <context_config.json> \
  --mart-dir <рабочий-каталог>/dm_res
```

3. Задать один вопрос о соответствии только тогда, когда сценарий сообщает, что
   SQL одинаково подходит нескольким таблицам. Не спрашивать соответствие только
   из-за одинаковых имён `DML_inc.sql` или `DML_arc.sql`.
4. Если S2T и формат уже получены, запускать проверку пакета даже при отсутствующем
   или неполном `dml_scripts.json`. Команда рассчитает ожидаемое количество и
   перечислит недостающие прототипы, не запуская DDL.
5. Для готового `dml_scripts.json` запустить:

```bash
bash {baseDir}/scripts/run.sh <S2T.xlsx> \
  --storage <iceberg|parquet> \
  --dml-json <dml_scripts.json> \
  --output-json <context_config.json> \
  --mart-dir <рабочий-каталог>/dm_res
```

6. При ошибке проверки показать пользователю весь полученный список исправлений.
   Не запускать DDL и последующие шаги после неуспешной проверки.
7. При успехе проверить наличие `context_config.json`, каталога `dm_res`,
   конфигурации каждого потока и всех файлов, указанных в `filePath` и
   `DqJsonPath`.
8. Передать пользователю оба результата: `context_config.json` и `dm_res`.

`dm_res` всегда должен называться именно так. Каждая пара `table.mode` должна
стать отдельным каталогом потока `<table>_<mode>`.

## Ограничения

- Не заменять готовые SQL-прототипы выдуманным SQL.
- Не принимать `SELECT *` или сочетание `*` с перечисленными полями.
- Не скрывать и не сокращать ошибки валидатора.
- Не менять порядок данных недетерминированными операциями.
- Не использовать интернет: зависимости устанавливать только из
  `{baseDir}/scripts/wheelhouse`.
- Не выполнять задачи, не относящиеся к сборке витрины данных.
